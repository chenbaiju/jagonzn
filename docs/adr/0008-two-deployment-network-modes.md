# JADR-0008：jagonzn 首版只规划公网双后端与全内网双后端

- 状态：已接受（2026-09-28，负责人将部署形态收敛为两种；仅设计，尚无目标环境验收）。
- 取代范围：[JADR-0007](0007-unified-console-and-backend-boundary.md)中“公网设备入口＋私网后端”、专线/隧道及私网 cloud 拉取作为首版推荐部署形态的表述；JADR-0007 的三个工程职责、统一前端、授权导入及数据权威继续有效。
- 依据：[jagonzn 主架构](../jagonzn-system-architecture.md)、[平台协议合同](../../../docs/device-integration/STANDARD_PROTOCOL_ACCESS.md)、[平台授权交付决策](../../../docs/adr/0227-self-hosted-issuer-console-and-delivery-media.md)。

## 四维审计

| 维度 | 结论 |
| --- | --- |
| 事实依据 | service 负责设备协议与技术事实，cloud 负责自己的业务数据库和 API，console 是统一浏览器前端。设备 HTTP、MQTT、TCP、CoAP 有不同传输与安全要求；签名授权在两种交付介质下使用同一运行时判定。 |
| 逻辑连贯性 | 两个后端各有公网主机不等于数据库、消息队列和所有管理端口都要公开；两者在内网但没有互联网不等于彼此断开。无互联网时不能要求联机兑换授权码，也不能从“同一局域网”直接推断事件和命令已通过认证与去重。 |
| 信息缺口 | 目标主机、两机可达地址、实际设备协议/端口、证书及设备信任链、console 访问域名或内网地址、在线签发出站及离线介质作业仍需部署时确认；本 ADR 不填入虚构配置。 |
| 观点区分 | 两种形态是负责人本轮明确选择；协议安全和双后端职责来自现行文档；按需开放端口、后端服务身份、失败回执与独立验收是本 ADR 的实施建议。 |

## 两种支持形态

| 形态 | 部署与管理 | 授权交付 | 必须验证的链路 |
| --- | --- | --- | --- |
| **公网双后端** | `jagonzn-service` 与 `jagonzn-cloud` 均可部署在有公网地址的服务器；`jagonzn-console` 通过受控 HTTPS 入口操作两个后端。仅公开实际需要的设备协议、受控业务/管理入口，数据库、Kafka、Redis、MinIO 不对公网开放。 | service 能出站访问 ThingsCloud 发行方时，管理员输入联网授权码，service 兑换并导入同一签名授权。 | 设备到 service、两后端双向业务 API/事件、console 到两个 API、service 到发行方；分别验证协议证书、身份、鉴权、失败及恢复。 |
| **全内网双后端** | 两后端及 console 在相互可达的局域网，无互联网；设备在可达内网接入。内网 HTTP 仍用 HTTPS，TCP/CoAP 仍按 TLS/DTLS 合同，证书信任由现场配置。 | 现场生成不含私钥的申请文件，经受控介质送达发行方；取得签名授权文件后带回，由本地管理员导入。无需在线码或发行方实时连接。 | 设备、console、service/cloud 间的内网路由与服务身份；离线导入、授权期限、重复、断线及恢复。 |

两种形态共用同一申请身份、签名 V1 文件、批准四档修订、原子导入与运行时计量。公网模式的 HTTPS 不能替代 MQTT/TLS、原生 TCP/TLS 或 CoAP/DTLS；公开地址不能让未认证的管理操作可用。全内网模式中的“无网”指没有互联网，两个后端仍须能通过局域网交换业务事件与命令。若它们连局域网也不互通，则只具 service 独立技术运行资格，不能按本形态声称 cloud 联动或统一前端已工作。

首版不安排“公网 service＋私网 cloud”、站点间隧道或 cloud 主动拉取等第三种交付组合。未来确有客户场景时再单独评审，不给当前两种形态增加前置。cloud 未部署时 service 仍可独立完成设备技术运行及授权恢复；双后端部署形态不改变这一既有职责。具体网络合同和分别验收按[SHC 工作包计划](../../../docs/reuse-entry/THINGS_CLOUD_REUSE_CLOSEOUT_AND_SELF_HOSTED_REVIEW.md)执行。
