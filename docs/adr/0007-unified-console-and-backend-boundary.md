# JADR-0007：jagonzn-console 统一前端与双后端职责

- 状态：已接受（2026-09-28，负责人明确 `jagonzn-console` 集成两个项目的 Web 操作；设计已确定，应用及界面尚未交付）。
- 依据：[JADR-0001](0001-service-cloud-responsibilities.md)、[JADR-0005](0005-signed-self-hosted-entitlement.md)、[平台 ADR0227](../../../docs/adr/0227-self-hosted-issuer-console-and-delivery-media.md)。

## 四维审计

| 维度 | 结论 |
| --- | --- |
| 事实依据 | service 独立承担设备运行和技术数据，cloud 将来承担人员/场所/开锁业务并有自己的业务库。service 现有受控 HTTP 管理 API，cloud 仍是无 HTTP 的骨架，`jagonzn-console` 尚不存在。 |
| 逻辑连贯性 | “service 不做网页”不等于可以删除其管理 API；无 cloud 时仍须完成初始化、申请、授权导入、诊断及设备管理。一个前端也不意味着两个后端共享数据库、JWT 或业务权限；设备公网入口也不等于后端进程必须直接暴露公网。 |
| 信息缺口 | console 与两个 API 的登录、令牌受众、代理路由和业务角色映射尚无正式跨服务合同；真实设备协议、端口、管理员访问位置及 service/cloud 间私网可达性未定。cloud 自身业务模型和交付时间也未确定。实施前须单独冻结，不用浏览器跨库访问填补。 |
| 观点区分 | 两后端数据与运行职责来自已接受 JADR；统一 `jagonzn-console` 且 service/cloud 均不提供独立浏览器页面来自负责人本轮裁决；首屏激活向导、无 cloud 时仅展示技术菜单及分阶段接入是本 ADR 的实施选择。 |

## 决策

`jagonzn-service` 是设备与平台技术能力后端，保留设备初始化、管理查询、授权状态、申请生成、联网兑换、离线导入、诊断和恢复所需的受控 HTTP API/运维命令；不在该服务内维护独立的浏览器管理页面。其设备数据、计量和授权导入状态以 service 的独立数据库为权威，协议和后台 Worker 不依赖网页或 cloud。

`jagonzn-cloud` 是后续业务后端，使用自己的业务数据库和 API，负责人员、场所、谁能开锁、授权时段、业务审计和处置；通过版本化 API/事件使用 service 的可信设备事实，不能直接读取或修改 service 业务表，也不接管设备协议、平台授权验签或技术额度。cloud 自身如需另售业务套餐，须单独决定，不能把人员开锁授权误当作 ThingsCloud 的自部署签名权益。

`jagonzn-console` 是计划新增的**唯一统一浏览器前端**：技术/设备与授权管理调用 service API，人员/场所/开锁业务调用 cloud API。初期只部署 service 时，console 可显示初始化、授权及技术管理；cloud 未交付或不可达时不阻塞 service 的设备运行和恢复。首次访问只引导受控本地管理员建立首个业务租户、生成部署申请、输入联网授权码或导入离线授权文件；不能要求在创建首个租户前先出示绑定该租户的授权。无有效签名授权时不自动转为 FREE，只保留初始化、授权、诊断和必要备份恢复入口；到期后的仅采集展示按平台 ADR0217 执行，不能整站锁死。

console 的统一视觉、导航和同源代理可由部署层提供，但这不自动赋予 cloud 访问 service 数据库或复用 service JWT 的资格。正式双后端登录/单点登录、令牌受众、跨服务角色映射、CORS/代理路径及审计必须形成独立合同并做越权验证；在此之前，console 可以先交付只连接 service 的授权与技术功能。service 即使没有 console，也保留管理员可用的受控命令或 API 恢复路径。

## 公网设备接入与私网业务部署

设备从互联网直接接入时，必须有设备可达的**协议入口**，但 service 进程不必直接运行在公网地址上。推荐在公网边界由网关/负载入口终止或转发实际启用的协议，再把流量送到受保护网络中的 service/EMQX；只开放 HTTPS 不能代替 MQTT/TLS、原生 TCP/TLS 或 CoAP/DTLS 的实际端口与路径。数据库、Kafka、Redis、MinIO、service 管理 API、授权导入 API 及 cloud 业务 API 不因设备接入而自动暴露公网。小型单机部署可以共址，但仍须隔离设备入口和管理入口，逐协议核验证书、路由和拒绝行为。

cloud 可以在没有公网入站的私有网络中运行。优先通过受控私网连接、专线或站点间安全隧道连接两个后端，使 service 的可靠事件推送和 cloud 的授权业务命令继续走已规划的 API/事件合同；console 部署在管理员可达的管理网络，经受控代理访问两个 API。若没有可达的私网连接，现有 service 主动 Webhook 不能直接投递到不可达的 cloud，须另行设计由 cloud 发起的可靠拉取/回执和命令提交合同，并验证去重、积压、重放与断线恢复。公网设备入口的 HTTPS 证书不能替代两个后端之间的身份与授权，也不能让浏览器自动越过私网边界。

联网授权码还要求 service 能向 ThingsCloud 发行方**出站**连接；设备能从公网进入本服务，不证明该出站链路可用。没有出站网络的现场使用离线文件。具体公网监听地址、协议、端口、证书、代理终止方式、管理网访问与云私网互通属于目标环境的部署输入，不能凭本 ADR 宣称已可部署或已取得公网验收。

两个后端与 console **都在不通互联网的同一可路由局域网**时，不需要公网设备入口，也不要求 ThingsCloud 发行方在线。设备按实际启用协议连接内网 service/EMQX；HTTP 仍为 HTTPS、原生 TCP 仍为 TLS、CoAP 仍为 DTLS，证书及设备信任链须在内网分发验证。管理员从内网访问 console，console 经受控管理路由访问两个后端；service 与 cloud 在内网交换可靠事件和业务命令，各自数据库仍隔离。现场生成 `.tcshreq` 并通过受控介质带到 ThingsCloud 发行方，取得签名授权文件后带回导入；联网授权码、在线续期、发行方实时获知导入结果和外部邮件均不可作为此形态的必备功能。到期时间仍由发行方签名决定，本地断网或导入日不重新起算。

若“两个都没有网络”还包括 **service 与 cloud 相互隔绝**，两后端不能即时交换事件或命令，console 也不能直接同时调用它们；此时只有 service 自身的设备技术闭环可独立运行。要完成业务联动须补通受控内网，或另立离线批量交接、冲突及结果回执合同；不能把单纯文件授权导入误认为业务链路已连通。内网形态的实际协议端口、局域网路由、内网证书、备份/恢复、授权文件交付及双后端断线回放须单独验收。

备选方案：把网页嵌入 service 会把前端构建绑到设备运行制品；让 cloud 成为唯一激活网关会使尚未部署的业务服务成为设备服务的启动前置；让 cloud 直接查询 service 数据库破坏双后端的数据权威。这三种方案均不采用。实施顺序及验收见[平台 SHC 计划](../../../docs/reuse-entry/THINGS_CLOUD_REUSE_CLOSEOUT_AND_SELF_HOSTED_REVIEW.md#4.%20自部署商用切片（SHC）)。
