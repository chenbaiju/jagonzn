# 多协议接入能力建设优先级与实施顺序

> 更新日期：2026-09-24
> 状态：开发者建议，待项目负责人裁定；不是已批准的实施计划。
> 执行边界：本文件只保存对后续能力规划的建议，不改变 ThingsCloud 当前实施阶段、门禁、切片、负责人或进度记录，不将以下工作插入当前执行轨迹。

> 负责人裁定：jagonzn 是 ThingsCloud 的租户，使用独立实例和同构的 `jagonzn` 数据库验证，禁止修改 ThingsCloud 的任何代码或数据库表。jagonzn 记录不足及建议，由 ThingsCloud 自行评审。厂商适配保持在自身项目，设备数据不运行时回传。详见[验证部署说明](tenant-validation-and-contract-evolution.md)及[独立反馈台账](PLATFORM_CAPABILITY_FEEDBACK.md)。

## 1. 建议结论

建议按以下顺序推进候选工作：

1. **保持当前已批准实施轨迹不变。** 多协议扩展先作为候选方向，不插入当前 ThingsCloud G3/其他既定切片，也不把阶段外规划写成已开始工作。
2. **如未来获批启动，先核对最小设备接入合同。** 确认已有接口覆盖的身份、属性、事件、命令及可靠性边界；缺失的公共语义形成反馈，不能在 jagonzn 内修改平台补齐。
3. **随后用一款设备做端到端垂直验证。** 验证其原始报文、平台身份、属性与事件上行、命令下行及设备结果闭环。
4. **根据验证结果登记通用扩展建议。** ThingsCloud 独立评审数据流和适配框架；jagonzn 不直接开发平台框架。
5. **之后按真实客户需求和硬件证据扩展协议覆盖。** 每种能力区分为原生标准协议、配置式数据流、厂商适配器、经具体型号/固件验证的兼容路径。

核心排序是：**核对并复用已交付能力 → 自身项目适配设备 → 验证可支持的闭环 → 登记不足和建议 → ThingsCloud 独立评审 → 如正式交付，再跟随基线复验**。任何阶段发现阻塞即可反馈，不能等完整闭环后才记录。当前阶段、状态和放行条件统一见[项目进度总览](PROJECT_PROGRESS.md)；本文只保留排序理由，不是另一份进度台账。

## 2. 排序依据

### 2.1 先处理平台共同缺口

当前 ThingsCloud 标准接入合同明确排除设备事件、自定义编解码、DTU 型号适配和任意厂商私有 TCP 帧；MQTT 事件 Topic 目前也没有通用事件标准化处理路径。烟感报警/恢复和智能锁开锁/异常记录均需要表达为逐次事件。

这里的缺口是设备自报事件的入口与业务处理路径。ThingsCloud 已有公共 Webhook 等平台对外集成能力，见 [S14-R8f-1 交付证据](../../docs/delivery/audits/S14-R8f-1-public-integration-evidence.md)；不能因此另起一套同用途公共投递机制，也不能把它当作设备事件上报入口。

如果先写完整设备适配器而没有稳定的事件与设备身份合同，可能只能把事件压成普通属性、暂时丢弃事件，或依赖平台内部实现。前两者会损失设备事实语义，后一种会增加平台能力扩展后的返工风险。

因此优先核对一条设备闭环的最小需求与已有能力差异。差异若必须修改平台才能解决，交由 ThingsCloud 评审；jagonzn 可以验证独立的解析和已支持路径，但不能绕过缺口或宣布完整闭环。

### 2.2 再做一个纵向样例

只做平台合同而没有设备纵向验证，容易对通用解析能力过度设计。第一款设备适配应能覆盖真实设备的身份、上下行与错误恢复，以证据检验合同是否充分，再决定抽象哪些能力。

首个验证设备应根据目标选择：

- 若目标是验证私有协议适配、短连接/休眠和厂商 ACK，4G 烟感具有代表性。
- 若目标是推进 jagonzn 智能锁首场景，简工智能锁更贴合业务目标；其 JT808 风格帧和锁型差异必须先核实具体型号、固件及标准符合性。

本建议不替项目负责人裁定首个设备，也不假定两款设备能够共用同一个帧解码器。

### 2.3 最后形成可扩展框架

烟感和智能锁的传输方式都是 TCP，但帧格式、身份流程、加密差异、消息应答和业务命令并不相同。先通过一款设备验证公共接入合同，再将稳定部分沉淀为扩展接口，可以降低把单一厂商特征错误抽象成通用规则的风险。

任意用户代码运行、插件位置（平台核心/外部网关）、编解码配置模型、兼容矩阵和事件通道都尚未冻结；本文件不替代这些设计裁定。

## 3. 候选任务及验收方向

| 顺序 | 候选任务 | 目的 | 初步验收方向 |
| --- | --- | --- | --- |
| 0 | 保持当前执行轨迹 | 不影响当前 ThingsCloud 门禁与已排定工作 | 不改当前阶段、切片、进度状态和放行结论 |
| 1 | 复用基线与冻结最小设备接入合同 | 建立独立运行基础和设备到平台的稳定连接点 | 先确认 JAR/迁移与隔离部署；设备实现前定义身份、事件、命令、受理/幂等及存储归属；冻结不等于入口已实现 |
| 2 | 单设备垂直适配验证 | 确认实际支持范围与闭环缺口 | 通过现有入口验证帧解析、身份、属性与适用命令；缺少事件等路径登记受阻，不改平台 |
| 3 | 登记可复用扩展建议 | 为 ThingsCloud 提供评审输入 | 厂商解析与平台接入分层；证据、影响、建议、已知限制有独立记录，评审不等于已交付 |
| 4 | 按需求增加协议 | 扩大已验证兼容范围 | 每种型号/固件有明确路径、能力边界和验证证据 |

设备适配细节在 jagonzn 自身范围冻结；平台数据库表、公共接口和插件 API 的变更由 ThingsCloud 自行评审与实施，不由本表授权或排期。

## 4. 实施前设计冻结事项

以下是相应工作的核对清单：阶段 1 核对交付和隔离部署，阶段 2 前核对设备合同、支持的存储入口与认证，阶段 4 汇总公共扩展建议，由 ThingsCloud 自行评审。缺少平台能力则登记受阻，不由 jagonzn 实现公共能力。首台自身适配器的运行位置需要先定，任意用户脚本或通用插件方案不作为阶段 1 的前置条件。完整阶段门见[项目进度总览](PROJECT_PROGRESS.md)。

- 适配器运行位置和责任边界；是否允许用户提供代码；代码如何隔离、签名、升级和回滚。
- 事件接入合同以及属性、事件、状态、命令、设备 ACK/最终结果之间的模型和可靠性语义。
- 厂商身份到平台 device/tenant/project 的可信绑定、密钥管理和权限边界。
- TCP 消息分帧、会话管理、短连接设备的命令排队和重试策略。
- 配置式解析、受控协议插件、外部网关的职责划分与支持/兼容声明规则。
- 首个试点设备、具体型号/固件、真实设备可用性和成功验收标准。

如以上定义出现文档矛盾或关键字段/接口仍缺失，应按项目既定设计冻结流程先提交裁定，不通过实现细节绕过。
