# 多协议接入、4G 烟感与 JT808 智能锁适配调研记录

> 记录日期：2026-09-24
> 状态：需求方向已明确；适配器接口、数据合同与实施方案尚未冻结。本文记录事实、差距和待裁定事项，不代表代码已实现或某个适配方案已获批准。

> 负责人已明确 jagonzn 不得修改 ThingsCloud 任何代码或数据库表。本文的公共事件、数据流、插件等建议交由 ThingsCloud 自行评审，相关不足与证据独立登记于[反馈文档](PLATFORM_CAPABILITY_FEEDBACK.md)；jagonzn 只在自身工程适配并验证现有支持范围。

## 1. 结论摘要

ThingsCloud 项目应面向持续增加的厂商设备协议，逐步具备可扩展的数据流接入和协议适配能力，并保留受控、可验证的支持范围。TCP 是当前烟感和后续设备协议的重要接入方式，但扩展目标不应局限于 TCP；传输协议、报文格式、厂商应用协议和平台业务语义需要分层描述。

4G 烟感协议资料已经提供，是一个明确的私有 TCP 协议样例。按现有 ThingsCloud 标准协议合同，它不能直接作为原生标准 TCP 设备接入：烟感使用厂商二进制帧、IMEI 识别及厂商应答码，而当前标准 TCP 要求 TLS、TC 固定帧和平台设备凭据。协议适配仍有价值；烟感帧解析及设备交互逻辑可复用，平台接入和数据语义映射则应依稳定的适配接口实现，避免绑定当前固定 TCP 帧内部实现。

## 2. 项目边界与当前实现

### 2.1 jagonzn 项目职责

- `jagonzn-service` 是目标中的独立 IoT 接入和运行服务，承载设备接入、数据处理、技术告警、命令和可靠转发。
- `jagonzn-cloud` 是后续定制化 SaaS，负责人员、场所、授权、业务审计和业务处置；当前没有开发排期。
- 两个应用仍是 Spring Boot 骨架，尚未接入 ThingsCloud JAR，也没有实现烟感协议适配。
- TCP 智能锁是既有业务场景，首台验证设备尚未裁定，见[项目进度](PROJECT_PROGRESS.md)；service 后续可接入其他厂商和协议。

依据：[jagonzn 双项目架构与分阶段实施方案](jagonzn-system-architecture.md)、[service 后端复用与独立部署方案](jagonzn-service-backend-architecture.md)。

### 2.2 ThingsCloud 当前接入边界

依据仓库内的[标准协议接入合同](../../docs/device-integration/STANDARD_PROTOCOL_ACCESS.md)和[设备接入指南](../../docs/device-integration/DEVICE_INTEGRATION_GUIDE.md)：

- 标准 HTTP、TCP、CoAP 路径围绕统一设备身份、属性上报、命令领取/推送和命令回复实现。
- 标准 TCP 使用 TLS、固定 10 字节 TC 帧头、约定帧类型和 JSON 业务载荷；它不是任意 TCP 字节流或厂商私有报文接收器。
- 合同明确排除了用户自定义编解码、DTU 型号适配、任意厂商私有 TCP 帧及设备事件上报。
- MQTT 指南中虽登记 `up/event/{eventKey}` Topic，但当前通用事件标准化器尚未实现，发送会进入 DLQ；不能把该 Topic 视为已可用的事件接入接口。
- Modbus 点位映射和轮询已在 S10 交付，但这不等于已经交付通用厂商协议插件或所有 Modbus/DTU 部署路径。
- TCP 多实例下行 D-190 已按方案 A 完成开发、验证并关闭；该状态不代表上述自定义 codec 或事件缺口也已关闭。
- TCP 已有 `ACCEPTED(0x13)` 受理确认；公共 Webhook 等平台对外集成也已有[本地交付证据](../../docs/delivery/audits/S14-R8f-1-public-integration-evidence.md)。设备自报事件接入与平台对外事件投递是不同方向，不能互相替代。

### 2.3 ThingsCloud 官网 TCP 资料的参考边界

2026-09-24 复核公开文档：TCP 接入页描述将设备类型的自定义数据流绑定到 TCP 通道，注册包格式为 `ProjectKey&AccessToken`；自定义数据流页分别列出 JSON、Plaintext、HEX 和 Modbus RTU，并可结合消息规则处理数据。HEX 是二进制报文的可读表示，选择该格式不等于平台已经理解某厂商的帧结构和业务语义。

参考链接：[设备 TCP 接入](https://www.thingscloud.xyz/docs/guide/connect-device/tcp.html)、[自定义数据流](https://www.thingscloud.xyz/docs/guide/device-type/custom-data.html)。这是对官网文档所述产品能力的记录，不应与本仓库固定 TC 帧的实现混为一谈，也不意味着任意二进制厂商协议无需解析、认证映射或业务适配即可完整工作。

## 3. 4G 烟感已知协议事实

来源为设备项目 `D:\Obsidian\azyv3\03_4G烟感\通信协议相关.md` 及其引用的厂商资料（包括《NB-IoT CAT1 数据格式 V3.17 客户》）。以下为当前资料中的记录，具体型号和固件差异仍须在接入验收时与真机报文核对：

- 设备使用 4G CAT1，通过 TCP 主动连接可配置的服务器域名和端口；厂商配置端口要求大于 1000。
- 报文是厂商自定义 HEX/二进制格式，资料记录 `0x72` 设备信息、`0x11` 应用/状态数据、`0x02` 命令下发、`0x03` 命令结果/应答等报文类别。
- 设备身份以 IMEI 为主要标识，平台按预录设备校验；现有资料未说明设备会发送 ThingsCloud `ProjectKey&AccessToken` 或当前仓库的 `{projectKey, deviceKey, secret}` 认证帧。
- 上报采用一收一答流程；厂商应答包含未登记 `AAAA0000`、已登记无待下发命令 `AAAA0001`、有待下发命令并保持唤醒 `AAAA8001` 等语义。
- 电池供电款可能在发送后断开并休眠，心跳默认约 22 小时；有待下发命令时平台需利用设备唤醒窗口排队、延迟发送并处理命令结果。
- `0x11` 报文中的状态和事件字段承载报警、恢复、电池、故障等设备事实。将其全部压成普通属性会损失逐次事件语义。

因此，烟感接入除了字段解析，还涉及身份绑定、上行应答时序、重复报文处理、短连接命令队列、事件归一化和命令回执。仅建立 TCP 连接或保存原始 HEX 报文不等于完整接入。

IMEI 登记属于标识绑定证据，不独自构成抗冒用的凭据认证。设备侧可信认证能力及接入信任边界仍需核实；不能默认已具备与 ThingsCloud secret 等价的安全保证。以上协议细节沿用已有资料调研，本次知识库审计未重新逐页核验原始 XLSX/DOCX，也未执行真机验收。

## 4. 面向后续设备协议的需求方向

用户已明确：后续会继续提供更多 TCP 设备协议；ThingsCloud 应逐步支持更多设备协议或自定义消息接入方式。平台方向应满足：

1. 新增某个厂商协议时，不应改写所有协议共享的身份、租户/项目范围、安全、配额、幂等、日志和持久交接逻辑。
2. 能区分原生标准协议、平台可配置的数据流、经版本化适配器接入的厂商协议，以及经真实型号/固件验证的兼容声明。
3. 将属性、逐次事件、状态、命令和命令结果归一到平台统一语义；保留厂商消息标识和必要的原始证据以支持追溯。
4. 支持范围必须有版本、测试样例和已知限制；未经真实设备验证的型号不得声明为已兼容。
5. 适配能力不能破坏现有标准 TCP 的 TLS、认证、可靠受理、幂等、租户隔离和多实例路由边界。

以上是能力目标，不等于已经选择了在核心进程运行插件、外部网关、声明式解析器或任意用户脚本中的某一种实现方式。

## 5. 烟感适配可复用性判断

### 可复用的设备协议部分

- 烟感帧结构与粘包/半包处理、`0x72/0x11/0x02/0x03` 报文解析和编码。
- IMEI 与设备资产的绑定规则、厂商应答码、`pkgSn` 去重和事件类型映射。
- 电池设备短连接、睡眠唤醒窗口、待下发命令排队、厂商级 ACK 和结果超时处理。
- 有来源和版本的原始报文样例，以及真机验证记录。

### 可能需要重做或调整的平台接入部分

- 如果解析、设备会话、ThingsCloud 固定 TC 帧、数据库写入和告警动作写在一个耦合服务中，未来切换到通用数据流/codec 接口时，平台桥接层需要重构。
- 如果现在把烟感报警只映射成属性，而未来新增原生事件合同，事件映射、持久化与调用链仍需调整。
- 若适配器持有 ThingsCloud 内部表结构或调用未承诺稳定的内部类，内核版本升级可能造成适配器重写。

判断：烟感适配不会因平台能力扩展而必然作废；独立的厂商协议解析资产可复用。是否需要二次适配取决于平台连接器是否遵循稳定、版本化的适配合同。当前并没有这样的合同，故完整生产适配器的接口设计尚未冻结。

## 6. 设计冻结前待裁定事项

开始实现通用适配框架或完整烟感业务闭环前，至少需要裁定：

- 适配器的运行位置：ThingsCloud 核心服务内、独立网关/sidecar，或两种模式并存。
- 哪些能力允许用户配置，哪些需要开发者编写并签名发布的协议插件；是否允许运行用户代码及其隔离边界。
- 统一消息合同如何表达属性、事件、设备在线状态、原始报文引用、命令、设备 ACK 和业务结果。
- 厂商身份如何安全绑定到平台 device/tenant/project，如何轮换凭据和限制适配器权限。
- TCP 数据流如何界定一条消息（长度、分隔符、协议解析或超时策略）、异常与重连如何隔离，短连接设备命令保存到哪里。
- 编解码器版本、兼容矩阵、真机资格、样例回放、性能/限流、审计和故障回滚如何定义。
- 用户自定义数据流首批格式与协议的优先级；JSON、Plaintext、HEX 属于载荷格式，Modbus RTU/TCP 属于应用协议，不能混作一层配置。

在这些事项裁定之前，本记录只作为需求与调研输入；不把任意用户脚本执行、通用 HEX 解析、事件接口或具体插件 API 记为已批准设计。

## 8. 简工智能锁 JT808 协议评估

### 8.1 文档中确认的协议特征

来源为 `D:\Obsidian\azyv3\01_安智云dev\2025-简工智能锁产品协议（JT808）.docx`。以下只概述该文件中的 TCP 锁协议部分；文档还包括 JT-BLE、JT-OTG 等不同通信章节，不应混作同一个 TCP 协议。

- 锁作为 TCP 客户端、平台作为服务端，连接成功后走设备注册与鉴权流程。
- TCP 帧使用 `0x7E` 起始标记和 `0x7D` 转义，包含消息 ID、消息属性、设备标识、流水号、消息体及校验；设备标识字段在该文件中按 IMEI BCD 表示。
- 文档列出注册 `0x0100`、平台注册应答 `0x8100`（返回鉴权码）、终端鉴权 `0x0102`、心跳 `0x0002` 与通用应答 `0x8001` 等交互。
- 业务消息涉及锁控制、锁状态/位置上报、开锁记录、低电和异常状态，并包括不同型号的升级和配置扩展。
- 文档明确存在不同锁型、固件及加密/校验差异；可见内容涉及 SM4 或 AES 类报文加密描述，不同型号的密钥和校验处理不应假设统一。原文含对称密钥材料，本知识库不复制密钥值；实现时须用受控密钥配置，并确认密钥轮换/泄露处置责任。

### 8.2 是否属于标准 JT/T 808

文档称其为“JT808 TCP 通讯协议”，并引用《交通部808全套协议规范.pdf》，但没有给出明确的 JT/T 808 版本及逐项符合性对照。交通运输部列出的 JT/T 808-2019 名称为“道路运输车辆卫星定位系统 终端通信协议及数据格式”，其标准背景是道路运输车辆定位终端；本文件面向智能锁，并包含锁业务消息和厂商扩展。因此在完成正式标准版本与帧字段的对照前，应称为“JT808 风格/兼容基础的智能锁厂商协议”，不能仅凭名称承诺是未经扩展的标准 JT/T 808 实现。

参考：[交通运输行业标准查询：JT/T 808-2019](https://jtst.mot.gov.cn/hb/search/stdHBDetailed?id=09b11ea9b3da0a9158124082fca512ce)、[交通运输部关于 JT/T 808-2019 修改单的公告](https://xxgk.mot.gov.cn/jigou/kjs/202111/t20211111_3625608.html)。

### 8.3 与当前 ThingsCloud 的兼容性

该锁和烟感一样，虽然都是 TCP 设备客户端，但不能直接使用当前 ThingsCloud 原生 TCP 协议：锁采用 `0x7E` 帧、厂商注册/鉴权和锁业务消息；ThingsCloud TCP 使用 TLS、固定 TC 帧、平台设备凭据及属性/命令 JSON 合同。若固件不能改为 TC 协议，需由网关/协议适配组件解析 JT808 风格报文并映射至 ThingsCloud 的设备身份、属性、事件和命令合同。

当前标准接入合同没有设备事件上报能力，MQTT 通用事件标准化器也未交付；因此开锁记录、异常开门等逐次事件不能仅靠 TCP 帧翻译就形成完整的平台事件闭环。还需为统一事件接入合同确定一个受支持的入口。

### 8.4 与烟感的异同及复用判断

| 方面 | 4G 烟感 | 简工智能锁 | 可复用判断 |
| --- | --- | --- | --- |
| 协议性质 | 厂商私有 CAT1 TCP 二进制协议 | JT808 风格并含锁型/厂商扩展 | 两者平台映射共性可复用，帧编解码不可互换 |
| 设备身份 | 主要按 IMEI 和厂商应答流程 | IMEI 字段、注册应答鉴权码和终端鉴权 | 可复用受控设备绑定原则，不能直接复用报文认证 |
| 上行事实 | 烟感状态、报警及恢复 | 锁状态、开锁记录、报警及位置 | 两者都需要逐次事件模型；平台事件入口目前缺失 |
| 下行特点 | 电池设备需利用短时唤醒窗口排队下发 | 锁控制及型号相关配置/升级命令 | 命令生命周期可共用，协议编码和设备应答需各自适配 |
| 适配资产 | 专属烟感帧解码、应答和休眠队列 | 可抽取 JT808 通用帧层，再加锁业务 codec | 若拆分帧层、设备协议层和平台连接器，未来较易复用；当前无冻结的插件 API |

锁适配的公共 JT808 帧层可能比烟感私有协议更容易扩展到其他 JT808 终端，但必须先核实具体标准版本、终端标识长度、消息体/校验/加密变体。当前可确认的是“需要适配”，不能据此承诺任意 JT808 设备自动兼容。
